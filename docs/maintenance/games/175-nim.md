## Gameplay and controls

Choose normal (last stone wins) or misere (last stone loses), then Play. Take 1, 2 or 3 using buttons or digit keys. The computer leaves a multiple of four in normal mode or one modulo four in misere whenever possible; losing-strategy positions use random moves. This is a perfect strategic response where a winning response exists, not a guarantee the computer wins every deal.

N starts another round; Escape at the result also starts another round, not Menu. New round and Menu are explicit buttons. The end overlay describes who took the final stone and offers Play again/Menu. No sound exists. Menu cancels the computer move; returning Play clears score and rounds.

## Audit findings

- **MEDIUM, static scoring:** `index.html`, `endRound`, anchor `if (moverWon)`: only normal-mode final movers increment a score. Misere correctly names the losing final mover but never awards the opponent a win, so completed misere games leave both scores unchanged. Root fix: compute winner from `(mode, mover)` and increment exactly that side once.
- **MEDIUM, static result focus:** `endRound` focuses Play again, but `startRound/toMenu` do not consistently move focus out of the hidden overlay/screen. Root fix: focus the live take button or Play/menu control at those existing transition functions.
- **LOW, static validation ceiling:** `take` does not reject `n > 3`, although every real caller supplies only 1 to 3. Not a remotely exploitable interface; if exposing the API later, enforce the complete rule in the shared function first.
- **Non-finding:** pending computer work is cancelled and guarded. No extra scheduler abstraction is needed for the current single timeout.
