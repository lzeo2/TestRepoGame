# Rare-answer trivia: multiplayer research and protocol

Research date: 2026-10-19. Operator's corrected brief supersedes the initial cell-arena interpretation. This is a mechanic-family clone with original content, not a reproduction of a reference game's questions, branding or art. Primary workload: seven 25-second questions, typed answers, curated rarity points, reveal and scoreboard, **2–12 players including host**. No typing stream or frame-by-frame sync.

## Decision and delivery boundary

1. **Phase 1: ship offline solo daily dives, numbered dives and themed packs.** Battle is explicitly unavailable, not a fake room-code UI. No transport or provider is initialized. The operator expressly permits Battle to remain phase 2.
2. **Recommended phase-2 internet transport: Supabase Realtime Broadcast, host-authoritative star semantics**, with individually authenticated anonymous identities, private authorized topics and host-only answer delivery. Public publishable/legacy anon keys are intended client configuration, not secrets [1]. Provisioning, policies, owner/privacy/budget decisions and real online acceptance are still required. No endpoint/account/credentials are supplied or created by this run.
3. **If trusted server enforcement is required, prefer Cloudflare Durable Objects**, with one authoritative room object and native WebSockets. More backend work, but simpler authority than trying to make a public client broadcast enforce rules [8].
4. **HTTPS commands plus durable-state polling** are a workable lower-complexity transport when an approved atomic backend already exists. Not a free stateless-function trick. On this Pages site, introducing Netlify just for this is additional infrastructure, not reuse of a functioning room service.
5. **BroadcastChannel is a local QA/practice option only.** Same-browser/profile/storage-partition tabs can communicate without a relay. It cannot reach a friend on another device, another browser profile, or the internet [9]. Do not present it as online Battle proof.
6. PeerJS/WebRTC are technically viable but add signaling and NAT traversal for a workload that does not need P2P latency. WebTransport is last: specialized server infrastructure without a trivia benefit.

No multiplayer was implemented or tested by this research. No estimated limit below is a measured capacity or latency SLA. Mutable sources were retrieved on the research date, not guaranteed for the remainder of 2026.

## Hosting reality and policy

GitHub Pages serves static HTML/CSS/JS, not a live function or room authority [10]. The repository's deployment guide identifies its Pages base; a research-lane HEAD request returned HTTP 200 with GitHub's server header. `netlify.toml` also retains root-publish/function configuration. Pages does not execute that configuration. The only tracked Netlify function, `netlify/functions/bare.js`, returns disabled-proxy status, not signaling or mutable game state. `/bare/*` remains disabled; no proxy, header, hosting or backend changes are proposed here.

A static frontend can contact a separately hosted approved WSS/HTTPS service. **That online mode is not offline.** Solo remains free of network dependencies. Runtime third-party prohibitions remain the default; this research does not silently amend repository policy. The operator's public-anon-key clarification is correct independently of network authorization. Existing GeoGuesser history demonstrates a Supabase implementation, but the inspected credits/commits do not establish standing approval for this new project. An old assertion that any runtime API key is a secret conflates public Supabase configuration with privileged keys. Never restore old credentials/endpoints or infer ownership from history.

## Signaling, NAT and school networks

WebRTC explicitly leaves signaling outside its API [11]. Manual signaling means exchanging complete SDP offer/answer blobs (wait for ICE gathering to finish for one copy/paste exchange). Each host/guest connection needs its own negotiation; one offer is not a reusable 12-person room. At 12 players a star requires 11 offer/answer pairs, 22 one-way transfers. A short room code needs a shared lookup/signaling service; encoding the entire SDP as a huge 'code' is not the same experience.

PeerJS Cloud is one published free signaling option, but offers no demonstrated numeric allocation or uptime commitment in the fetched pages [14]. Firebase Realtime Database Spark can carry signaling or, more sensibly here, room state: 100 simultaneous connections, 1 GB storage and 10 GB/month downloads, shared project quotas [20]. Firebase rules and identities still need configuration; Spark is not a promise of free custom Cloud Functions scoring. Supabase can also carry signaling, but using its room events directly avoids an unnecessary WebRTC layer.

No STUN/TURN means host candidates only. Some routable environments may succeed beyond a LAN, but ordinary NAT/CGNAT reachability is not established. STUN discovers mapped addresses, **not a relay**; TURN relays when direct connectivity fails [12]. School client isolation can prevent two devices on the same SSID from communicating even while both can reach the web [13]. Schools may also block UDP, WSS or service domains. No transport guarantees bypassing these controls; do not weaken school security. Outbound approved relay connections avoid peer-to-peer reachability requirements, not content filtering.

Direct peers may learn endpoint IPs; signaling/ICE providers see metadata; TURN relays encrypted transport but still sees endpoints/timing. Manual SDP should not be publicly posted or logged. Encryption does not make room invitations authenticated.

## Supabase quota arithmetic and privacy

Supabase charges Broadcast as one sent event plus each delivered event [3]. For seven questions and 12 sockets, assuming self-echo and all messages on one topic:

- Two state events, 12 submissions and 12 acks/question: `26 × 13 = 338` events/question, **2,366/game**, before joins/recovery/overhead.
- Twelve simultaneous submissions alone: `12 × 13 = 156` events, potentially above Free's 100/s. Low average frequency is not enough.
- Isolated host-only submissions/player-only acks: `2 × 13 + 12 × 2 + 12 × 2 = 74` events/question, **518/game**, with a maximum illustrative combined burst under 100 before other traffic. Must measure actual accounting and stagger/back off under shared project load.
- 200 connections theoretically fit sixteen full 12-person rooms, leaving eight; this is arithmetic, **not a safe production capacity promise**. Presence, extra tabs, reconnects and other rooms need headroom.

Do not send answer text on an all-room topic and merely hide it. Use Auth identities and private `realtime.messages` policies with host/player topic permissions [2]. A room code locates/invites; it does not prove host or player identity. `ack: true` confirms broker receipt, not host acceptance. API keys identify the application; bare anon callers do not have distinct identities. Anonymous sign-in avoids email/password but creates a provider identity; its documented IP signup limit can affect school NATs. Do not generate a new identity on every reconnect.

Free Supabase projects may pause after insufficient database activity for a week; **Broadcast-only traffic is not a documented keep-awake guarantee** [4]. Show service unavailable and require owner resume, not stealth pings. Recheck limits, account eligibility, project region, age/terms, spend controls and retention before provisioning. No automatic paid upgrade.

Game payloads should use generated aliases, ephemeral player IDs, bounded answers, no chat, no emails and no analytics. Do not claim 'no personal data': IP metadata, pseudonymous IDs and answer content may identify people. Provider/host access logs remain; GitHub Pages itself documents visitor IP logging [10]. All hosted modes expose connection metadata to the provider; exact retention must be owner-reviewed. Prefer short-lived rooms with verified deletion and no answer/token logs. Supabase publishable/anon keys are public by design; service-role, secret keys, signing secrets, Pusher secrets and Ably API secrets must never ship.

## Why serverless echo is not a room

Netlify describes an ephemeral request runtime [15]. A warm in-memory map can disappear or differ between concurrent instances. An echo only replies to its caller; it provides neither shared state nor atomic submit locks. Long-poll/SSE has duration/reconnect costs and is not duplex WebSockets. Provider support says no hosted WebSocket server; the support post is historical, while current function docs still do not document a persistent room listener.

Modern streaming docs say 60 s/20 MB; Lambda-compatibility streaming docs say 10 s/20 MB. The repository uses a compatibility-signature handler, currently non-streaming. Do not promise the larger limit indiscriminately. Background execution up to 15 minutes does not hold a live response [16].

Netlify Blobs defaults to eventual propagation up to 60 s. Current docs advertise strong reads and atomic conditional writes (`onlyIfNew`, ETag `onlyIfMatch`), but also retain contradictory last-write-wins limitations prose [17]. Verify chosen SDK/deployed CAS semantics, or use a transactional store. Strong reads alone do not prevent lost updates. No store is configured here.

At 12 players polling every 2 s: 21,600 requests/room-hour, 4.32 request credits alone. At 5 s: 8,640, 1.728 credits. Compute/storage/transfer/commands/deploys are extra; these are not measured costs. IP-only throttles must account for many students sharing a NAT [18]. Pages cannot run this backend; functions in Git do not provision one.

## Concrete phase-2 protocol: host-authoritative, not mesh

Friendly-game trust model: host can inspect local answer keys and cheat, as can any player reading shipped data. No tournament anti-cheat claim. Stronger enforcement requires a server scoring authority and controlled question delivery, not obfuscation.

- **Dataset**: versioned curated local prompt IDs and tiered recognized answers; no live rarity analytics. Seven stable question IDs/seed/version are pinned at room creation. Host is one of 2–12 roster slots. Daily UTC date does not change a running game.
- **Envelope**: `{v:1, room, match, round, seq, type, requestId, payload}`. Validate exact type/range, bounded strings and maximum 8 KiB serialized size; never trust claimed sender ID, score, deadline or host role. Identity comes from authorized topic credentials.
- **Topics**: authorized host-only submission inbox per participant; participant-only ack inbox; room-wide state topic where only host may publish. Policies bind membership/host roles to authenticated IDs, not caller-writable role fields. Room creation/join/capacity and role grants need an authorized atomic operation. A six-character locator is not sufficient access control.
- **Lobby**: host creates random room/match identifiers and expiring invitation; join operation assigns a stable slot/identity, refuses >12, and returns current full snapshot. Late joins spectate until next match. No free-text names required.
- **Question start**: host sends full revisioned state, prompt ID, `startsAt`, `deadlineAt`, seven-round index and current scoreboard. Clients animate countdown locally, not by network ticks. Approximate clock offset via request/response midpoint, display latency caveat; host's receipt clock governs acceptance. No speed bonus.
- **Submit**: at most one accepted answer/player/round, ≤80 Unicode characters after trim; identical `requestId` retries return the original ack. Host checks membership, matching match/round, open phase and receipt before deadline. Ack is `accepted`, `late`, `locked` or `invalid`. Pending is not accepted; client button disabling alone is not a lock. Never trust client timestamps.
- **Reveal**: at deadline (not early merely because some players finished), freeze unanswered slots as zero, compute curated-tier points once, then publish recognized answer, points, depth and cumulative scoreboard. A monotonic revision prevents stale/reordered messages rolling state back. Maximum 700 points/7,000 metres; depth is 10 metres per point.
- **Recovery**: after reconnect, request full host snapshot; never replay closed-round queued answers. Heartbeats about every 10 s while connected, 30 s host-loss timeout, explicit ended/unavailable state; close sockets on leave. No automatic host migration in first version. Keep local solo independent of all provider code.
- **Abuse/privacy**: enforce private send/receive policies, immutable locks, per-identity rate limits, expiring room membership, minimal retention; do not broadcast hidden answers, credentials or arbitrary user HTML. Verify policy denials against nonmembers and spoofed host/player packets.

Acceptance before enabling Battle: real two-browser internet-relay exchange with no BroadcastChannel fallback; 12-client simultaneous-submit bursts; duplicate/changed retry; late packet and old-round rejection; host disappearance; reconnect/stale revision; policy denial and pre-reveal confidentiality; service paused/quota errors; zero-network solo. Same-host clients prove protocol, **not real multi-device/school-network reachability**. None is claimed yet.
